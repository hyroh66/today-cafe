# TODAY CAFE — 2026 겨울 신메뉴 이벤트 및 실시간 주문 관리 웹서비스 PRD

> 문서 버전: 1.0  
> 작성 기준: 사용자와 진행한 **1~10차 기획 협의 확정 사항**  
> 문서 상태: **개발 착수용 초안** (미확정 정책은 별도 표시)  
> 구현 대상: Codex 기반 웹서비스 개발  
> 기준 시간대: `Asia/Seoul`

## 1. 제품 개요

### 1.1 목적
사내 직원 및 외부 방문객이 TODAY CAFE의 신메뉴 출시 이벤트를 확인하고, **실시간 할인 잔여 인원**을 보면서 모바일 중심의 단일 페이지에서 즉시 주문할 수 있도록 한다. 카페 담당자는 별도의 인증된 관리자 페이지에서 주문을 접수·준비·완료·수령·취소 처리하고, 선착순 잔여 인원을 관리한다.

### 1.2 핵심 원칙
- **이벤트 홍보와 즉시 주문을 통합**한다. 온라인 결제는 제공하지 않으며 **현장에서 결제**한다.
- 실시간 잔여 인원은 화면 장식이 아니라 **서버가 관리하는 정확한 수치**여야 한다.
- 동시에 마지막 자리를 신청한 경우에도 정해진 한도를 초과하지 않도록 **원자적 트랜잭션**으로 처리한다.
- 각 이벤트는 서로 독립적이며, 같은 사람이 하루에 각 이벤트를 1회씩 주문할 수 있다.
- 고객 정보는 최소한으로 수집하고, 관리자 작업은 기록한다.

## 3. 상품·할인·한도

| 이벤트 코드(제안) | 고객 표기 | 정상가 | 할인 | 최종가 | 1일 할인 한도 |
|---|---|---:|---:|---:|---:|
| `PERSIMMON_LATTE` | 아이스 홍시라떼 | 5,000원 | 1,000원 | **4,000원** | **20명** |
| `CARROT_CAKE` | 무가당 오가닉 당근케이크 | 5,000원 | 1,000원 | **4,000원** | **20명** |
| `SET` | **아이스 홍시라떼 + 오가닉 당근케이크 세트 특가** | 10,000원 | 3,000원 | **7,000원** | **20명** |

### 3.1 가격 및 주문 규칙
1. 세트 할인 3,000원은 **두 메뉴를 세트로 구매할 때만** 적용하며, 개별 메뉴 할인과 **중복 적용하지 않는다**. 따라서 세트 결제액은 7,000원이다.
2. 세트와 각 단품은 **서로 독립된 이벤트**이다. 동일 고객이 같은 날 **아이스 홍시라떼 1개 + 당근케이크 1개 + 세트 1개**를 각각 주문하는 것은 허용한다.
3. **고객 1명당 이벤트별 하루 1개 또는 1세트**만 할인 주문할 수 있다. 동일 이벤트의 수량을 2개 이상 신청할 수 없다.
4. 한 번의 주문에 여러 이벤트를 함께 선택할 수 있으며, 각 이벤트의 선착순 인원은 **독립적으로 1명씩** 차감한다.
5. 각 이벤트의 기본 일일 한도는 **20명 고정**이다. 관리자에게 한도 증액/감액 권한을 제공하지 않는다.
6. 기본 한도를 전부 사용할 경우 이벤트별 남은 수량은 0으로 표시하고 해당 이벤트의 주문을 비활성화한다.
7. 최대 **일일 60건의 이벤트 참여 슬롯**(3종 × 20명)이며, 하나의 고객 주문에 여러 슬롯이 포함될 수 있으므로 **주문번호 개수와 반드시 같지는 않다**.

### 3.2 선착순 수량 계산
- 이벤트 날짜·이벤트 코드 단위로 `capacity = 20`을 적용한다.
- 주문 **확정 순간** 해당 이벤트의 잔여 수량을 차감한다. 결제 또는 수령 시점까지 차감을 미루지 않는다.
- 취소되더라도 **관리자가 수동 복구 승인하기 전에는 수량을 반환하지 않는다**.
- 관리자가 취소 주문에 대해 수량을 복구하면 **승인 즉시** 해당 날짜·이벤트의 잔여 수량에 반영한다.
- 같은 취소 항목을 **두 번 복구할 수 없다**. 수량은 20을 초과할 수 없다.
- 매 영업일의 한도는 독립적이며, 이전 영업일 잔여 인원이 다음 날로 이월되지 않는다.
- 신규 주문 및 수량 복구는 모두 **동시성 안전한 데이터베이스 트랜잭션**으로 처리한다.

### 3.3 주문 중복 및 재주문
- 동일 고객의 중복 판단 키는 **정규화한 휴대전화번호 + 주문 영업일 + 이벤트 코드**이다.
- 확정되거나 처리 중인 동일 이벤트 참여 기록이 있으면 같은 날 같은 이벤트를 다시 주문할 수 없다.
- 고객이 주문을 취소하면, **잔여 수량이 있는 경우 동일 이벤트에 재주문 가능**하다. 다만 취소 슬롯의 수량 복구는 관리자 결정이므로, 복구 전에는 다른 남은 슬롯이 있어야 재주문할 수 있다.
- 한 번에 여러 이벤트를 주문하는 경우 고객이 일부 이벤트만 다시 선택하는 상황도 서버에서 검증한다.
- 단순 전화번호 입력은 본인 확인을 보장하지 않으므로 실제 운영 전 추가 인증·부정 주문 방지 필요성을 검토한다.

## 4. 주요 사용자 및 이용 시나리오

### 4.1 고객
1. 카페 행사 페이지에 접속한다.
2. 메뉴 사진·가격·이벤트 기간 및 **각 메뉴 카드의 실시간 잔여 인원**을 확인한다.
3. 원하는 이벤트 1~3개를 선택하고 이름, 휴대전화번호를 입력한다.
4. 주문 가능 날짜·시간과 중복 주문 여부·남은 인원을 최종 확인한 후 주문을 확정한다.
5. **날짜+일련번호 형식**의 주문번호(예: `1201-001`)를 큰 글씨로 확인한다.
6. 주문 상태를 **접수 → 준비 중 → 준비 완료 → 수령 완료**로 확인한다.
7. 준비 완료 시 페이지 내 알림과 브라우저 알림, 지원 환경에서 소리 알림을 받는다.
8. 카페 메인로비 1층에서 주문번호를 제시하고 **현장 결제** 후 메뉴를 수령한다.
9. 나중에 **휴대전화번호 + 주문번호**로 주문을 다시 조회한다.
10. 관리자가 **준비 시작 전**이면 고객이 직접 취소할 수 있으며, 취소 내역도 확인할 수 있다.

### 4.2 관리자
1. 관리자 ID·비밀번호로 로그인한다.
2. 신규 주문을 **실시간 화면 팝업 + 알림음**으로 확인한다.
3. 주문 목록에서 고객 주문번호·메뉴·상태를 확인한다.
4. 접수 주문의 준비를 시작하고, 완료 후 `준비 완료`, 현장 결제·수령 후 `수령 완료`로 처리한다.
5. 고객 취소 내역을 확인하고 필요한 경우 **수량 복구 버튼**을 눌러 잔여 인원을 복구한다.
6. `19:00` 이후 미수령 주문을 **미수령 목록**에서 확인하고 건별로 최종 처리한다.
7. 수량 복구와 기타 주요 관리자 작업의 **변경 이력**을 확인한다.

## 5. 고객용 화면 요구사항

### 5.1 페이지 구조 — 단일 페이지
- 브랜드 헤더: TODAY CAFE **텍스트 로고**.
- 메인 히어로: 겨울 신메뉴 홍보 문구, 이벤트 기간, AI 생성 상품 이미지.
- 상품 카드 3개: 메뉴명, AI 이미지, 정상가, 할인가, 할인액, **실시간 남은 인원**, 주문 선택 상태.
- 세트 카드는 반드시 **“아이스 홍시라떼 + 오가닉 당근케이크 세트 특가”**로 표기한다. “오늘의 세트 특가”만 단독 표기하지 않는다.
- 주문 영역: 선택한 상품, 합계 금액, 이름·휴대전화번호, 개인정보 수집·이용 안내, 주문 확정.
- 주문 확인 영역: **큰 주문번호**, 주문 상품, 현장 결제 예정 금액, 상태 단계, 취소 가능 여부.
- 기존 주문 조회: 휴대전화번호와 주문번호 입력.
- 방문 안내: 메인로비 1층, 08:00~19:00, 주말·공휴일 휴무.

### 5.2 표시 및 예외 상태
- 영업 중이며 잔여 인원이 있는 카드: 주문 선택 가능.
- 해당 이벤트 마감: 잔여 `0명`, **선착순 마감** 안내, 해당 카드 선택/주문 불가.
- 영업 외 시간 또는 행사 기간 외: 영업·이벤트 종료 안내, 신규 주문 불가; 기존 주문 조회는 제공.
- 실시간 연결이 끊긴 경우: 임의의 수량을 '실시간'으로 표시하지 않는다. 마지막 동기화 시각 또는 업데이트 실패 표시 후 새로고침/재시도 수단 제공.
- 주문 확정 경쟁으로 재고가 소진된 경우: 서버 응답에 따라 오류를 안내하고 현재 수량 다시 표시.
- 중복 주문으로 거절된 경우: 동일 날짜·이벤트의 주문 제한을 분명하게 안내.
- 주문 실패/네트워크 재시도 상황에서 **중복 주문이 생성되지 않도록 멱등성**을 확보한다.

### 5.3 브라우저·소리 알림
- 고객의 주문이 `준비 완료`로 바뀌면 **페이지 내 상태와 알림 배너**가 갱신된다.
- 브라우저 알림 권한은 사용자가 명시적으로 허용한 경우 요청·사용한다.
- 소리 알림은 사용자의 브라우저 상호작용/알림 활성화에 따라 가능한 경우에만 재생한다.
- 브라우저 백그라운드, 화면 종료, 권한 거부, 자동재생 제한 등의 환경에서는 알림/소리가 보장되지 않는다. **주문 조회 화면의 상태 표시가 항상 기준**이다.
- 실제 브라우저 푸시가 필요할 경우 HTTPS 및 서비스 워커/푸시 구성 여부를 기술 설계에서 확정한다.

## 6. 관리자 화면 요구사항

### 6.1 인증·권한
- 관리자 **ID와 비밀번호** 로그인.
- 비밀번호는 평문으로 저장하지 않고 강력한 일방향 해시로 저장한다.
- 관리자 API 및 관리자 데이터에 대한 접근은 서버에서 권한 검증한다.
- 세션 만료·로그아웃·로그인 시도 제한을 제공한다.

### 6.2 대시보드·목록
- 새 주문 실시간 알림: **팝업 + 알림음**.
- 주문 상태별 조회: `접수`, `준비 중`, `준비 완료`, `수령 완료`, `취소`, `미수령`.
- 이벤트별 현재 남은 인원과 당일 사용 인원 확인.
- 주문번호/일시/상품/고객 정보/상태로 주문 식별.
- 취소된 주문의 **취소 내역 목록**과 **수량 복구 여부** 표시.
- 미수령 주문 목록 및 관리자 후속 처리.
- 주문별 상태 변경·수량 복구 **감사 로그** 조회.

### 6.3 주문 상태 전이
```text
접수 ──관리자 준비 시작──> 준비 중 ──관리자 처리──> 준비 완료
  │                                           │
  └──고객 취소 가능──> 취소                    └──현장 결제·수령──> 수령 완료

19:00 이후 아직 수령 완료되지 않은 주문 → 미수령 목록에서 관리자 확인
```
- **고객 직접 취소는 `접수` 상태에서만 가능**하다. `준비 중` 이후 직접 취소 버튼은 숨기거나 비활성화하며 서버에서도 거절한다.
- `취소` 시 할당 수량은 즉시 복원하지 않는다. 관리자 수량 복구 승인이 별도로 필요하다.
- `미수령`은 관리자 운영상 별도 분류로 관리한다. 기존 주문의 실제 마지막 처리 상태와 이력을 유지하고, 관리자 판단 없이 자동 취소·자동 수량 복구하지 않는다.
- 19:00 이후 미수령 분류 대상과 수령 완료 처리 예외는 운영정책 보완 사항(§11)을 따른다.

## 7. 데이터 모델 (논리적 요구사항)

> 아래는 구현 가이드용 논리 모델이며, 실제 DB 테이블·필드명은 개발 시 결정한다.

- **Event**: 이벤트 코드, 표시명, 가격, 할인 가격, 이벤트 기간, 고정 일일 한도(20).
- **DailyEventQuota**: 영업일, 이벤트 코드, 한도, 소비된 슬롯, 복구된 슬롯, 갱신 시각. 날짜+이벤트 코드 고유 제약.
- **Order**: 내부 고유 ID, 표시용 주문번호, 주문 일시, 이름, 휴대전화번호(보호 저장), 합계 금액, 상태, 현장 결제 및 수령 처리 시각, 취소 시각.
- **OrderItem**: 주문 ID, 이벤트 코드, 수량(항상 1), 확정 당시 금액, 슬롯 할당 상태, 복구 여부.
- **AdminUser**: 관리자 ID, 비밀번호 해시, 계정 상태, 로그인 관련 정보.
- **AuditLog**: 관리자, 작업 종류, 대상 주문/이벤트/영업일, 이전값/이후값, 수행 시각, 복구 사유.
- **NotificationEvent**(필요 시): 주문 상태 변동 시각, 브라우저 알림 표시를 위한 이벤트 메타데이터.

### 7.1 정합성 요구사항
- 주문번호 예: `MMDD-001` (`1201-001`). **날짜별 일련번호 발급은 원자적으로 처리**하고 중복되지 않아야 한다.
- 표시용 주문번호 외에 **연도를 포함하는 내부 고유 식별자**를 둔다.
- 복수 상품 주문은 **전체 성공 또는 전체 실패**로 처리한다. 상품 일부만 차감되고 주문 전체가 실패하는 상태를 허용하지 않는다.
- 고객 주문 확정, 슬롯 차감, 주문번호 할당은 일관된 트랜잭션 경계 안에서 수행한다.
- 수량 복구도 중복 승인 방지 조건과 감사 로그를 포함해 원자적으로 처리한다.
- 수량은 항상 `0 ≤ 남은 인원 ≤ 20`을 유지한다.

## 8. 보안·개인정보 보호

- 고객에게 이름·휴대전화번호를 받기 전 **수집 목적, 수집 항목, 보유·이용기간 및 관련 안내**를 명확히 표시한다.
- 합의한 내부 운영 목표: **이벤트 종료 후 30일 이내 개인정보 삭제**. 다만 실제 적용은 법령상 보존 의무, 분쟁 대응 필요성, 파기 예외 여부를 검토한 뒤 확정한다.
- 이벤트 종료일은 2026-12-15이며, 30일 이내 삭제 운영 일정을 설정한다.
- 관리자 외에는 다른 고객의 개인정보를 조회할 수 없게 한다. 전화번호는 관리자 목록에서도 필요 최소한만 표시하고, 전송 중 암호화(HTTPS)를 적용한다.
- 고객 조회는 **전화번호 + 주문번호**를 요구하며, 무차별 대입·대량 조회 방지(요청 횟수 제한, 오류 메시지 통일, 접근 기록)를 적용한다.
- 고객 직접 취소는 민감한 변경 동작이므로 조회 정보만으로 취소를 허용할 때의 위험을 검토한다. **추가 확인 수단(예: 주문별 취소용 비밀 토큰 또는 휴대전화 인증)**은 구현 전 확정이 필요한 보안 항목이다.
- 관리자 ID·비밀번호를 프런트엔드 코드나 공개 저장소에 하드코딩하지 않는다.
- 고객 개인정보 삭제 시 백업·로그·알림 데이터의 처리 범위도 점검한다.

## 9. 비기능 요구사항

### 9.1 실시간성
- 잔여 인원 및 주문 상태는 서버 데이터를 기준으로 갱신한다.
- WebSocket, SSE 또는 짧은 간격의 폴링 등 **구현 기술은 미확정**이며, 정합성을 유지하면서 운영 복잡도를 낮추는 방식을 선택한다.
- 실시간 UI 데이터는 참고 표시이고, **최종 주문 확정은 항상 서버의 재검증**을 통과해야 한다.

### 9.2 사용성·접근성
- **따뜻한 감성형**의 크림·홍시 오렌지·브라운 팔레트를 사용한다.
- AI 생성 이미지가 실제 판매 모습과 다를 수 있음을 고려하고, 필요하면 이미지의 연출 여부를 표기한다.
- 휴대전화에서도 주문번호·가격·남은 인원·주문 상태가 쉽게 보이도록 반응형 UI로 구현한다.
- 버튼·폼 라벨·오류 메시지는 명확히 표시하고, 키보드 사용 및 충분한 텍스트 대비를 지원한다.

### 9.3 운영 안정성
- 서버의 대한민국 시간대·공휴일·영업시간으로 주문 접수 가능 여부를 판단한다.
- 네트워크 재시도, 동시 주문, 주문 도중 품절, 관리자 중복 클릭, 실시간 연결 단절을 안전하게 처리한다.
- 관리자 알림음 및 고객 알림음은 브라우저의 자동재생 정책을 준수한다.

## 10. 필수 인수 테스트 (Acceptance Criteria)

1. **단품 가격**: 홍시라떼와 당근케이크 각각 정상가 5,000원/할인가 4,000원으로 표시한다.
2. **세트 가격**: 세트는 정상가 10,000원/할인가 7,000원으로 표시하며, 단품 할인과 중복되지 않는다.
3. **세트 명칭**: `아이스 홍시라떼 + 오가닉 당근케이크 세트 특가`가 화면에 명시된다.
4. **일일 한도**: 영업일마다 3개 이벤트 각각 20명 한도가 독립적으로 적용된다.
5. **중복 제한**: 동일 휴대전화번호는 같은 날짜에 각 이벤트를 1회만 유효하게 주문할 수 있다.
6. **복합 주문**: 고객이 세 이벤트를 한 번에 선택하면 주문번호 하나가 발급되고 각 이벤트 한도가 각각 1명씩 차감된다.
7. **동시성**: 잔여 1명 상황에서 동시에 여러 주문을 제출해도 성공하는 것은 1명분뿐이다.
8. **취소**: 접수 상태 고객 취소는 가능하고 준비 중 이후 고객 취소는 불가능하다.
9. **수량 복구**: 취소만으로 잔여 인원이 늘지 않으며, 관리자가 복구 승인하면 즉시 1명 증가한다. 중복 승인은 차단한다.
10. **취소 후 재주문**: 취소 확정 후 같은 날짜·이벤트의 잔여 인원이 있으면 재주문할 수 있다.
11. **주문번호**: `1201-001`과 같은 번호를 발급하고 주문 완료/조회 화면에서 크게 보여준다.
12. **주문 조회**: 전화번호와 주문번호가 일치할 때 해당 주문의 내역/상태를 보여준다.
13. **상태 처리**: 접수 → 준비 중 → 준비 완료 → 수령 완료 상태가 고객에게 표시된다.
14. **고객 알림**: 준비 완료 시 페이지 표시가 갱신되며, 허용된 환경에서 브라우저·소리 알림을 시도한다.
15. **관리자 신규 주문 알림**: 신규 주문이 관리자 화면에 팝업 및 알림음으로 표시된다(허용된 환경 기준).
16. **미수령**: 영업 종료 후 미수령 주문은 관리자가 확인할 수 있는 별도 목록에 나타나고 자동 취소되지 않는다.
17. **영업시간**: 영업일 08:00 이전, 19:00 이후, 주말·공휴일, 이벤트 기간 밖에는 신규 주문이 거절된다.
18. **관리자 권한**: 일반 고객은 주문 상태 처리·수량 복구·개인정보 포함 주문 목록에 접근할 수 없다.
19. **로그**: 관리자 수량 복구의 담당자·일시·대상·사유·전후 값이 기록된다.
20. **개인정보**: 수집 안내, 보관·삭제 정책, 마스킹 및 보호 조치를 확인한다.

## 11. 개발 전 확인할 미확정 항목

다음은 **1~10차에서 확정되지 않은 사항**이다. Codex는 이를 사용자 확정사항으로 간주하거나 임의로 기존 정책을 변경하면 안 된다.

| 항목 | 현재 상태 | 제안 또는 확인 필요 사항 |
|---|---|---|
| 11차 세부 디자인 | 미확정 | 애니메이션 종류, 모바일 하단 고정 주문 버튼, 관리자 화면 세부 레이아웃 |
| 기술 스택/호스팅 | 미확정 | 프런트엔드·백엔드·DB·실시간 갱신·호스팅 및 예상 운영비 |
| 관리자 초기 계정 | 미확정 | 안전한 초기 관리자 계정 생성/비밀정보 관리 |
| 공휴일 데이터 | 미확정 | 대한민국 공휴일 데이터 공급·관리 방법 |
| 고객 취소 추가 인증 | 미확정 | 전화번호+주문번호만으로 취소할 때의 보안 보완책 |
| 주문 재시도 방지 | 기술 설계 필요 | 멱등성 키 및 트랜잭션 구현 방식 |
| 주문 일부 취소 | 미확정 | 여러 이벤트를 한 주문에 담았을 때 일부 항목만 취소 가능한지 |
| 19시 미수령 분류 | 세부 정의 필요 | 어떤 상태를 미수령로 표시할지 및 영업 종료 직전 주문 처리 방법 |
| 현장 결제 상태 | 미확정 | 결제 완료와 수령 완료를 함께 처리할지 별도 상태로 둘지 |
| 주문번호 연도 구분 | 내부 구현 필요 | 같은 `MMDD-순번` 표시가 다른 연도에 재등장해도 내부 ID로 구별 |
| 알림 전달 보장 범위 | 제약 있음 | 브라우저 푸시/알림·소리 제한, 탭 닫힘 시 알림 여부 |
| 개인정보 삭제 예외 | 법적 검토 필요 | 법정 보존 의무, 운영 로그/백업 정리 범위 |
| 이미지 생성물 | 제작 필요 | AI로 홍시라떼·당근케이크·세트 이미지 생성 및 최종 승인 |

## 12. Codex 구현 지침

1. 이 문서를 **제품 요구사항의 기준 문서**로 사용한다.
2. §2~§10의 **확정된 운영 규칙**을 우선 구현한다.
3. §11의 미확정 항목은 개발 전 사용자에게 확인하거나, 구현에 필요한 경우 **명시적 가정 및 변경 가능한 설정**으로 분리한다. 특히 결제 방식·할인 금액·선착순 한도·주문 취소/복구 정책은 임의 변경하지 않는다.
4. 백엔드/DB 중심으로 일일 한도, 중복 주문, 취소 복구, 상태 변경, 관리자 권한을 검증한다. 프런트엔드만으로 이를 관리하지 않는다.
5. UI에는 **실제 데이터가 아닌 수량·주문번호를 운영 값처럼 하드코딩하지 않는다**. 예시 데이터는 개발 및 테스트 환경에서만 사용한다.
6. 환경변수와 비밀정보를 공개 저장소에 포함하지 않고, 운영 환경에 HTTPS를 적용한다.
7. 인수 테스트와 동시성 테스트를 수행한 뒤 운영 배포를 검토한다.

---

**범위 참고:** 이 PRD는 사용자가 명시적으로 요청한 **1~10차 기획 확정 내용**만 제품 기준으로 통합한 문서다. 11차 질문에 제시되었지만 답변으로 확정되지 않은 옵션은 필수 요구사항으로 승격하지 않았다.
